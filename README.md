# CpuPLFix

修复 **Intel 笔记本开机 / 睡眠唤醒后 CPU 被锁在 0.55GHz** 的小工具，顺带管 **EC 风扇曲线** 和
**过热保护**（防止摸到固件的 `_HOT` 阈值被强制休眠）。

症状：开机或唤醒后 CPU 频率被钉在很低的水平（0.55 / 0.8 / 1.0 GHz），风扇不转、温度不高，但什么都卡。
重启或者手动在 ThrottleStop 里点一下能好，下次又犯。

本工具做成**常驻服务 + 计划任务双保险**，直接写内核寄存器（以及 EC 寄存器）：

- **开机**：服务在系统启动约 24 秒后完成修复（此时 Windows 自身才刚启动完）
- **睡眠唤醒 / 休眠恢复**：服务订阅了系统电源事件，**1 秒内**响应；另有轮询兜底，最坏 5 秒
- **风扇**：默认每 15 秒按 EC 温度写一次档位（EC 是慢总线，能少碰就少碰；刚开机 / 过热时会自动加密），
  比原生 EC 曲线（几乎是一条平线）热得多就快得多
- **过热保护**：温度到阈值立刻压功耗墙 + 风扇满速，必要时（可配）主动优雅休眠

不需要你手动干预，也不需要 ThrottleStop 常驻。

## 原理

Intel 平台的封装功耗墙（PL1 长时 / PL2 短时）在硬件里存了**两份镜像**：

| | 位置 | 谁在用 |
|---|---|---|
| 系统侧 | `MSR 0x610` (PKG_POWER_LIMIT) | Windows / ThrottleStop |
| 固件侧 | `MCHBAR + 0x59A0` (MMIO 镜像) | 主板 / EC 固件，bit63 是锁定位 |

正常情况下两份应该一致。但有些机器的固件会在开机和唤醒时把 MMIO 那一份改成一个很小的值，
CPU 就被钉在最低频。

在 ThrottleStop 里勾选 TPL 窗口的 **MMIO Lock** 之所以能修好，就是因为它把正常值写回 MMIO
再把 bit63 置 1 —— 锁上之后固件再也改不动，所以必须重启才能恢复原样。

本工具做同一件事，只是无界面、开机自动跑。

在作者机器上（Lenovo Ice Lake）实测：

```
修复前  MSR 0x610 : PL1 55.00W  PL2 55.00W  lock=0
        MMIO 0x59A0: PL1 21.00W  PL2 55.00W  lock=0   <-- 被固件压低
修复后  MMIO 0x59A0: PL1 55.00W  PL2 55.00W  lock=1   <-- 倍频回到 4.8GHz
```

## 用法

1. 下载本仓库（`Code` → `Download ZIP`），解压到任意目录
2. 双击 `1-install.bat`，UAC 弹窗点"是"

**不需要安装 ThrottleStop**，驱动已经内置在包里。

其它脚本：

|---|---|

| `3-fix-now.bat` | 立即修复一次 |
| `4-风扇状态.bat` | 只看风扇档位 / 转速 / EC 温度 |

> 这些脚本都会自己提权（双击 → 重新以管理员身份开一个窗口），所以能看到完整输出。

## 它怎么随系统启动（开机 / 睡眠唤醒 / 休眠恢复）

装好之后有**两套互相独立的机制**，任何一套单独都能把问题修好。

### 一、常驻看守服务 `CpuPLFixSvc`（主用）

Windows 服务，启动类型「自动」，由服务控制管理器在开机早期拉起 —— 不需要用户登录、
不弹窗、没有控制台窗口。

1. 等驱动可用（最多 180 秒）
2. 立刻检查 MMIO 功耗墙，不对就重写 + 上锁
3. 之后常驻，按下面的"轮询节奏"分频跑（每轮：过热门限 → 对齐功耗墙 → EC 温度 / 风扇曲线 / 固件标志）

**睡眠 / 休眠唤醒后怎么发现？** 两条路，先到先算：

| 路径 | 机制 | 延迟 |
|---|---|---|
| 路一（快） | 订阅 `SERVICE_ACCEPT_POWEREVENT`，系统恢复时主动通知服务 | **≤1 秒** |
| 路二（兜底） | 轮询 + 时钟跳变检测（挂起期间时钟会跳一大截） | ≤5 秒 |

### 轮询节奏：`poll_s` / `ec_poll_s` / `flag_poll_s`

三条时间线分开跑（都在 `config.json`，改完不用重启服务）：

| 循环 | 默认 | 碰什么 |
|---|---|---|
| 主循环 | 5 秒（`poll_s`） | 只碰 MSR / MMIO：过热保护定级、对齐功耗墙与电源档。**不碰 EC** |
| EC 读 | 15 秒（`ec_poll_s`） | EC 温度 `0x78` → 风扇曲线写 `HFSP(0x2F)` |
| 固件标志 | 30 秒（`flag_poll_s`） | 过热标志 `0x89` / `0x8A` / `0x8B` |

自动加密（内部按 `poll_plan()` 算，无需配置）：**开机 / 唤醒后的前 5 分钟** = 2 / 5 / 10 秒；
**过热保护已生效**时 EC 与标志都提到主循环同频；**EC 温度 > `guard.flag_hot_c`（默认 85°C）**时标志跟 EC 同频。
睡眠 / 挂起事件会清掉计时 → 唤醒后强制整套重读，不会拿旧温度用。

> **为什么分频**：EC 端口是和主板固件、系统自己的 ACPI EC 驱动共用的**慢总线**（见下文"EC 端口事务必须串行"）。
> 原先每 3 秒全读一遍 ≈ **2.67 次事务/秒**；现在 ≈ **0.47 次/秒**（约 1/5.7），
> 过热保护期间回到 ≈2.0 次/秒（宁可多读也不能漏掉固件翻脸）。
> 代价只是温度采样变稀（最坏一个 `ec_poll_s` 才看一眼，风扇响应相应变慢）；**功耗墙不受影响**（仍是 5 秒）。
> 想更省就调大 `ec_poll_s` / `flag_poll_s`；想完全不碰 EC：`fan.mode = "off"` + `guard.enabled = false`。

### 二、计划任务 `CpuPLFix`（兜底，四个触发器）

| 触发器 | 时机 |
|---|---|
| `BootTrigger` | 开机 +1 秒，并在开机后 30 分钟内每 5 分钟重复 |
| `LogonTrigger` | 用户登录 +3 秒 |
| `EventTrigger` | `Power-Troubleshooter` 事件 1（从低功耗状态恢复）+3 秒 |
| `EventTrigger` | `Kernel-Power` 事件 107（系统已从睡眠状态恢复）+3 秒 |

触发后先预检，状态正常就立刻退出（不占 CPU）；异常才修复，然后看守 4 分钟，
防止固件在这段时间里再补一刀。

两个机制做的事完全一样，且幂等 —— 重复执行没有副作用。

> 开了「快速启动」时点「关机」再开机走的是 `BootTrigger`，同样会被检查。

**怎么确认唤醒后真的检查了** —— 看 `logs\fix.log`：

```
[*] 收到电源事件 0x0012 (自动唤醒), 判定刚从睡眠/休眠恢复, 立即重新检查
[*] 检测到 830 秒挂起间隔, 判定刚从睡眠/休眠恢复, 立即重新检查
[*] 进程启动(睡眠/休眠唤醒后): 系统已运行 3600.2 秒, 解释器启动耗时 0.03 秒
```

## 关于驱动

读写 MSR 和物理内存必须有内核驱动。本工具**已内置** `TSCtl.sys`，安装时复制到工具目录
并注册成服务 `TSCtl`，之后由计划任务按需拉起。

这个驱动来自 ThrottleStop（作者 Kevin Glynn）——ThrottleStop 把它作为资源内嵌在自己的
exe 里，本工具按 PE 结构把 x64 镜像连同 Authenticode 签名一起提取出来，一个字节都没改，
只换了个文件名（否则会和 ThrottleStop 自己的设备名冲突）。选它是因为它是少数既能通过
现代 Windows 驱动签名校验、又同时提供 MSR / 物理内存 / PCI 配置访问的现成驱动。

> **装好本工具后可以直接卸载 ThrottleStop**，两者互不影响。驱动文件 `TSCtl.sys` 就在工具
> 目录下，服务名 `TSCtl`，跟 ThrottleStop 的临时驱动没有任何关联。

已知限制：如果机器开了 **内核隔离 / 内存完整性（HVCI）**，Windows 可能拒绝加载这类
直接访问物理内存的驱动，安装会失败。需要先关掉内存完整性再装。

`CpuPLFix.py` 里另外保留了 `_extract_driver_from_exe()` 作为兜底：万一 `TSCtl.sys`
丢了，而本机恰好有 `ThrottleStop.exe`，工具会自动从里面重新提取一份。

## 关于安全性

工具的原则是**镜像系统自己的设置**，不是超频：

- MSR 里的 PL1 是正常值 → 原样写进 MMIO，一个瓦都不改
- 只有 MSR 本身也被压坏（低于 `min_pl1_w`，默认 15W）时，才用 CPU 标称 TDP 兜底

CPU 自身的热保护（温度墙、EDP 电流墙）完全不受影响，该降频还是会降频。

### 两种工作模式：`mmio_mode`

```json
{
  "pl1_w": 40,            // 插电(AC)高性能档: 长时功耗墙(瓦)
  "pl2_w": 64,            // AC 档: 短时功耗墙(瓦)，0 = 自动取 max(PL1×1.25, 25)
  "pl1_w_batt": 28,       // 电池平衡档: 长时功耗墙(瓦)，0 = 电池也用 AC 档
  "pl2_w_batt": 55,       // 电池档: 短时功耗墙(瓦)
  "pl1_time": 35,
  "pl2_time": 66,
  "min_pl1_w": 15.0,      // 判定 MSR 是否异常的阈值
  "lock_mmio": true,
  "mmio_mode": "disable"  // disable = MMIO清零+锁后只写MSR(推荐); value = 写目标值进MMIO+锁
}
```

> **`disable`（默认，推荐）**：开机时把固件侧 MMIO `0x59A0` 清零 + 锁死（等于把固件侧
> 永久禁用），之后**所有档位只写 MSR `0x610`**。前提是 MSR 可写——ThinkPad 上实测
> 可写（写后回读确认）。收益：
> - **改配置免重启**：config 改完 1 分钟内生效，不用重启
> - **拔/插电真无缝**：拔电立刻切 28/55，插电立刻回 40/64，不受开机状态限制
> - 电池开机也无坑：开机锁的是"禁用"而不是某个低值，插电能直接升回去
>
> **`value`（老方案）**：把目标值写进 MMIO 再锁。锁死后档位不可变，改配置、改档位都
> 要重启；切档只能往低调（CPU 取 `min(MSR, MMIO)`），往上调被锁卡住。MSR 被 BIOS
> 锁死写不进的机器只能用这个模式。

> 填了具体数字就是**精确目标**，调高调低都会生效（安全下限 5W）。
> `disable` 模式下不再有"改完必须重启"的限制；`value` 模式仍然要。
> 切档实时代理是 `min(MSR, MMIO)`：MMIO 禁用后 MSR 就是唯一控制点。

## 技术细节：ThrottleStop 驱动的 IOCTL 表

驱动是 WinRing0 派生的，但 **IOCTL 编号被作者全部改掉了**，WinRing0 的标准码全部返回
`STATUS_UNSUCCESSFUL (0xC0000001)`。作者用 capstone 反汇编定位出来的：

`DriverEntry` (RVA `0x1730`) → `MajorFunction[14]` (RVA `0x1EF0`) → 范围校验
`add eax, 0x7FFF9BD0` → 有效码区间 `0x80006430..0x800064A4`，
二级跳转表在 RVA `0x2524`(byte 索引) / `0x24F4`(dword 偏移)。

| 功能 | IOCTL | 输入 / 输出 |
|---|---|---|
| 版本 | `0x80006494` | 空 → u32 |
| RDMSR | `0x80006448` | `u32 msr`（in len=4）→ `u64`（out len 必须=8） |
| WRMSR | `0x8000644C` | `{u32 msr; u64 value}` 共 12 字节 |
| 读物理内存 | `0x80006498` | `u64 物理地址` → 1/2/4/8 字节 |
| 写物理内存 | `0x8000649C` | `u64 地址` + 值（in len = 8+N） |
| 读 PCI 配置 | `0x800064A0` | `{u32 addr; u32 offset}`，`addr = bus \| dev<<8 \| fn<<16` |
| 写 PCI 配置 | `0x800064A4` | 同上 + 值 |
| 读 I/O 端口 | `0x80006430` | `u16 port` → 1/2/4 字节 |
| 写 I/O 端口 | `0x80006434` | `u16 port` + 值 |

读物理内存内部走 `MmMapIoSpace(addr, size, MmNonCached)` → 读/写 → `MmUnmapIoSpace`，
所以直接拿它操作 MMIO 是安全的。

## 风扇曲线（EC 寄存器 `HFSP` 0x2F）

Windows 里没有可调项：联想 Vantage 没有散热 UI，电源模式切"平衡 / 最佳性能"实测同温转速只差
0.1%（3460 vs 3464 RPM）。风扇转速完全由 EC 寄存器 `HFSP` 决定，所以工具直接写它。

| HFSP | 实测转速 | 说明 |
|---|---|---|
| `0x01` | 2480 RPM | 最安静 |
| `0x02` | 2610 RPM | |
| `0x03` | 2720 RPM | |
| `0x04` | 3190 RPM | |
| `0x05` | 3185 RPM | |
| `0x06` | 3490 RPM | |
| `0x07` | 3880 RPM | 原生曲线的天花板 |
| `0x40` | 4980~5020 RPM | 真满速（原生自动永远到不了） |
| `0x80` | — | 交还 EC 自动 |

原生自动曲线实测几乎是平的：EC 54°C → 3861 RPM，硬扛满载到 99°C 也只有 3896 RPM。这就是
"机器很烫但风扇不响"的原因。

默认曲线（`config.json` → `fan.curve`，`[[温度上限, 档位], ...]`）：

```
≤50°C → 1 档    50~58°C → 2 档    58~66°C → 4 档
66~74°C → 6 档  74~82°C → 7 档    >82°C → 满速(0x40)
```

实测：51°C 1 档（2471 RPM，比原生安静）→ 67°C 4 档 → 77°C 7 档 → 85°C 以上满速；
96°C 时 4983 RPM；降温自动退回。降温回差 `fan.hyst`（本机 3.0°C）防止边界抖动。

实现细节：底层用驱动提供的**端口 I/O** IOCTL（读 `0x80006430` / 写 `0x80006434`，
写入必须是 5 字节 `u16 port + u16 pad + u8 value`），再按 ACPI EC 标准协议（命令口 `0x66`、
数据口 `0x62`、`0x80` 读 / `0x81` 写）读写寄存器 `0x2F`，温度读 `0x78`，转速读 `0x84/0x85`。

换到没有这颗 EC 寄存器的机型上，工具只是不动作（`4-风扇状态.bat` 显示"读取失败"），
功耗墙部分不受影响。

### EC 端口事务必须串行（实测踩过的坑）

服务、命令行、临时脚本读写 EC 走的是同一套四步端口事务（写 `0x80` → 写偏移 → 等 IBF 清 → 读数据）。
实测：**两个进程同时做这套事务会互相插队**，读到的是对方那次事务的应答 —— 满载扫描时 `0x78` 读出
46 而同一刻服务读到 82，整段数据全不可信。因此：

- 每个事务先拿一把跨进程命名互斥体 `Global\CpuPLFix-EC`（服务与命令行共用；`Global\` 才能跨会话，
  服务在 session 0、bat 在用户会话）。拿不到就退化成不加锁，不影响功能。
- 关键读数（温度 `0x78`、标志 `0x89/0x8A/0x8B`）做**一致性校验**：连读两次一致才认，否则加大等待重试；
  仍不一致就当"这次没读到"（沿用上一轮判断），绝不拿垃圾值改保护等级。
- 每次读之前先等一会儿（3 ms，重试时 8/20 ms）：EC 满载时自己忙不过来，不等就会读到上一次留在输出缓冲
  里的**残留字节**（实测"读 `0x8A`"读到的是 `0x7A` 的值 46，且连读两次一样）。
- 温度突变过滤：相邻两次真读之间（默认 15 秒）跳 15°C 以上当可疑值，本轮沿用上一次，下一轮还是这样就认。
  （EC 读间隔拉长后这个窗口更严，代价只是延迟一轮，方向是安全侧。）
- 固件标志必须**连续两轮真读都读到**才动手，单轮毛刺只记一行提示；
  "沿用缓存标志"的那一轮（`flags_fresh = False`）**既不算命中、也不清零** —— 否则在 30 秒的标志节流下，
  真置位要等 60 秒才确认。

另外：**别用 WMI 的 `MSAcpi_ThermalZoneTemperature` 读热区温度** —— 本机那个查询会把调用方永久
挂死（实测卡住一个后台进程 20 分钟，只能强杀）。本工具走 EC 寄存器 + DSDT 反汇编，不碰它。

## 过热保护（防止固件强制休眠）

本机固件设了 ACPI 热区 `\_TZ.THM0` 的 `_HOT = 401K`（≈127.9°C），热区摸到它就**直接强制休眠
（S4）**。2026-10-18 12:43 跑满载时实测触发过一次，系统日志原文：

```
由于严重的热事件，系统已进入休眠状态…
高级配置和电源接口热区域 = \_TZ.THM0  _HOT = 401K      (Kernel-Power 事件 88 / 42)
```

**固件到底按什么判**：把本机 DSDT 里 `\_TZ.THM0` 的反汇编翻出来（`_TMP` / `_CRT` / `_HOT` /
`TC2K`）后，结论跟"两边差多少度"这种线性想法完全不是一回事：

- `_TMP`（热区报给系统的温度）平时返回的就是 EC `0x78` 换算出来的值：`温度 = 0x78 * 10 + 2732`
  （单位 0.1K，所以 `0x78` 本身就是摄氏度）；`_HOT = TCRT - 1 = 4010`（401.0K ≈ 127.9°C）。
- 但"温度路线"根本走不到 4010：`0x78 = 127` 只能算出 400.2K，而 `0x78 = 128`（`0x80`）是固件
  约定的**无效码**，AML 会把它当成 48°C。光靠温度值，热区永远到不了 `_HOT`。
- 真正让 `_TMP` 直接返回 `_HOT` 的，是 **EC 自己的过热标志寄存器**：

  ```asl
  Local1 = RBEC(0x89) & 0x7F
  Local2 = RBEC(0x8A) & 0x7F
  Local3 = RBEC(0x8B) & 0x7F
  If (Local3) { ... Return (TCRT - 1) }      // 直接报 _HOT
  If (Local1) { ... Return (TCRT - 1) }
  ```

  这三个寄存器（低 7 位）任一非零，热区立刻被报成 127.9°C，系统和固件随即执行强制休眠。
  **那次强制休眠是它们触发的，跟当时 `0x78` 读 99 还是 120 无关。**

所以保护分两条线：

| 线 | 依据 | 作用 |
|---|---|---|
| 温度线（主力） | EC `0x78` | 提前降温：砍功耗墙 + 风扇拉满（`0x78` 跟热区同源，但量程上限只到 ~99） |
| 固件标志线（最高级） | EC `0x89` / `0x8A` / `0x8B` 低 7 位 | 固件已经在报 `_HOT` 的最后信号：压到最低功耗墙 + 风扇满速，可按配置主动优雅休眠 |

默认阈值（`config.json` → `guard`）：

| 等级 | 触发 | 动作 |
|---|---|---|
| 预警 | EC ≥ 95°C | 功耗墙压到 PL1=20W / PL2=28W，风扇满速 |
| 严重 | EC ≥ 98°C（或 CPU DTS ≥ 97°C） | 功耗墙压到 PL1=10W / PL2=14W，风扇满速 |
| 固件标志 | `0x89/0x8A/0x8B` 任一低 7 位非零 | 同"严重"，并按需主动休眠（`escape_hibernate`） |
| 逃生 | EC ≥ 105°C | 维持最低功耗墙；`escape_hibernate=true` 时主动优雅休眠 |
| 解除 | EC ≤ 78°C | 恢复原 AC / 电池档 |

温控这两档的瓦数 = **插电档的 50% / 25%**（PL1、PL2 同比例缩）：插电 40W/55W → 预警 20W/28W、
严重 10W/14W。降频线和温控线是**同一套数**，顶都是 55W（固件原厂值）。

> 阈值怎么定的（诚实版）：EC 内部那颗真正决定"什么时候置标志"的传感器我们读不到，所以温度线
> 只能是**提前降温**，不是精确卡阈值。95/98 是照本机自己的数定的 —— 40W 满载 + 满速风，EC 温度
> 稳定平台就是 **~92°C**；CPU 自己的硬上限 TjMax = **100°C**，实测约 99°C 就撞温度墙（它自己会降频）。
> 95 只比正常平台高 3 度（环境热 / 风道堵才会碰到），不跟正常满载打架；98 卡在 CPU 自己动手前面。
> 笔记本被动降温的通行触发点也在这个 95~100 区间 —— 别往下调到 93 那种值，那等于"只要持续满载
> 早晚压到 20W"，把 `pl1_w=40` 废掉。真正把温度打下来的是功耗墙（发热由功耗决定），风扇只是辅助
> （原生自动曲线几乎是平的：54°C→3861 RPM，99°C→3896 RPM）。`recover_c=78` 是有意的，压到 70 会让
> 20W 状态在大热天长时间不解除。不想让固件标志参与判级，把 `guard.trip_flags` 改成 `false`。

保护只影响进程内状态，不改 `config.json`；解除后自动恢复，不需要重启。日志每级留一行，
`2-check.bat` 会显示"最近一次保护记录"和三个标志寄存器当前值。

## 已知限制

- 只处理 PL1/PL2 这条路径。如果是 **BD PROCHOT**、温度墙、电池/适配器识别问题导致的降频，
  本工具管不了，那种情况还是得用 ThrottleStop 排查。
- MMIO 功耗墙寄存器按 `0x59A0` 处理（Intel 近几代通用）。如果你的机器偏移不同，
  `2-check.bat` 会显示读不到或数值明显不对。
- CPU 被锁在 0.40GHz 时 Windows 自身启动就慢十倍，用户态程序只能等系统把服务拉起来。
  从按下电源到修复完成，本机实测 **23.5 秒**（服务）/ 24.0 秒（计划任务跟上时发现已好），
  做不到"零延迟"。睡眠/休眠唤醒不受此限制 —— 服务本来就活着，1~5 秒补锁完成。
- 如果机器开了 **内核隔离 / 内存完整性（HVCI）**，可能拒绝加载直接访问物理内存的驱动。
- 过热保护是"提前降温"而非"精确卡阈值"：EC 内部那颗真正决定何时置 `_HOT` 标志的传感器读不到，
  只能靠 EC 温度（`0x78`）提前动手 + 固件标志（`0x89/0x8A/0x8B`）兜底。极端情况（散热口被捂住 /
  环境 40°C 又跑满 AVX）仍可能摸到 401K，想更早降温可以把 `guard.warn_c` 往下调一点（比如 93），
  代价是持续满载更容易被压功耗；正常环境下建议维持 95/98。
- 风扇控制绕过 EC 自己的调速逻辑直接写档位；写错了跑一次 `7-风扇交还EC自动.bat`（写 `0x80`）
  即可完全恢复，不会损坏硬件。
- `guard.escape_hibernate` 默认 `false`（不主动休眠）。想让它真到 105°C 就替你休眠，改成 `true`。

## 开发 / 验证脚本（`dev/`，不是工具的一部分）

| 脚本 | 干什么 | 怎么跑 |
|---|---|---|
| `dev\selftest.py` | **离线自检**：不碰硬件，验证过热保护的分级/解除/标志线（含"单轮毛刺不动作"）和风扇降档回差。改完保护逻辑先跑它 | `"%APPDATA%\CpuPLFix\runtime\python.exe" dev\selftest.py`（普通权限即可） |
| `dev\ec_scan.py` | **EC 寄存器扫描**：空闲全貌 + 满载曲线（每 4 秒一采，关键寄存器带一致性校验），找"固件到底盯哪颗传感器"。有安全阀（标志出现或 `0x78>=97` 立刻撤负载） | 管理员权限跑；结果写 `dev\ec_scan_out.txt` |

> `ec_scan.py` 适合看**趋势**，不适合当精确标定：负载很重时 EC 自己忙不过来，个别读数仍可能拿到
> 输出缓冲里的残留字节（脚本会把"两遍 dump 不一致"的寄存器标出来，一眼能看出数据可不可信）。
> 它扫出来的本机结论（寄存器表、负载下没有超过 99 的寄存器）记在维护手册的《风扇与过热保护》里。
