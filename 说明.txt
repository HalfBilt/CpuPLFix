CpuPLFix —— 功耗墙修复 + EC 风扇曲线 + 过热保护
==================================================================

（前身只修"开机 / 睡眠唤醒后 CPU 被锁在 0.4~0.8GHz"；现在同一个工具还管
  风扇转速和过热门限，三个功能共用同一个看守服务，开机后自动生效。）

【症状】

笔记本开机后、睡眠唤醒后、或者休眠恢复后，CPU 频率被钉在最低档（常见 0.40GHz /
0.55GHz / 0.80GHz）。风扇不转、机器不热，但什么都卡，连任务管理器都要转半天。
重启有时能好，有时重启反而更糟，下次又犯。


【原因】

Intel 平台的"封装功耗墙"(PL1 长时 / PL2 短时)在硬件里存了两份镜像：

    1) MSR 0x610          —— CPU 内部寄存器，Windows 和 ThrottleStop 读的是这一份
    2) MCHBAR + 0x59A0    —— 主板/EC 固件用的那一份(MMIO)，bit63 是"锁定位"

本机实测(健康状态)：
    MSR  0x610     = PL1 55W / PL2 55W / 未锁
    MMIO +0x59A0   = PL1 55W / PL2 55W / 未锁

但某些机器的固件会在开机和唤醒时，把 MMIO 那份的 PL1 改成一个小得离谱的值。
本机抓到的两次现场值：

    较轻的一次：PL1 = 21W   → 全核约 1.8GHz
    严重的一次：PL1 =  5W   → 倍频直接掉到 4，也就是 0.40GHz

CPU 实际执行的是 MMIO 那份，所以无论你怎么在系统里改，都改不动它。

在 ThrottleStop 里勾选 TPL 窗口的 "MMIO Lock" 之所以能修好，就是因为它把正常值写回
MMIO，再把 bit63 置 1。锁上之后固件再也改不动，所以必须重启才能恢复原样。

本工具做的是同一件事，只是不需要图形界面、开机就能自动跑。


【怎么用】

    1. 把整个文件夹解压到任意固定位置（路径别带空格更省事）
    2. 双击 1-install.bat
    3. 弹出"用户账户控制"时点"是"
    4. 看到 [√] 已生效并锁定 就装好了

之后不用管。

其它脚本（都需要管理员权限，双击后会弹一次"用户账户控制"）：

    2-check.bat        查看当前状态（功耗墙 / 频率 / 风扇转速 / 温度 / 过热保护）
    3-fix-now.bat      立即修复一次（降频时手动救急用）
    4-风扇状态.bat     只看风扇与温度
    5-风扇曲线.bat     风扇回到"按温度自动"（推荐，默认就是这个）
    6-风扇满速.bat     风扇固定满速（约 5000 RPM）
    7-风扇交还EC自动.bat  交还给 EC 自己的曲线（本机原生曲线偏平，到不了满速）
    8-风扇固定档.bat   手动指定 EC 档位（1~7 或 64）
    9-uninstall.bat    卸载（删除服务、计划任务，不删文件）


【它现在是怎么随系统启动的】

装好之后有两套机制在守着，互相独立，任何一套单独都能把问题修好。

一、常驻看守服务 CpuPLFixSvc（主用，最快）

    这是 Windows 服务，启动类型"自动"。系统一启动，服务控制管理器就会把它拉起来，
    不需要用户登录、不弹窗、没有控制台窗口。

    它启动后做四件事：
      1. 等驱动可用（开机早期最多等 180 秒）
      2. 立刻检查 MMIO 功耗墙，不对就重写 + 上锁
      3. 每轮读一次 EC 温度：过热门限到了就压低功耗墙（见【过热保护】）
      4. 每轮按温度曲线写一次风扇档位（见【风扇】）
      之后一直常驻：前 5 分钟每 2 秒一轮，之后每 3 秒一轮

    睡眠 / 休眠唤醒后怎么发现？两条路，先到先算：

      路一（快）  服务订阅了 Windows 电源事件 SERVICE_ACCEPT_POWEREVENT。
                  系统从睡眠或休眠恢复时会主动通知服务，服务立刻重新检查，
                  通常在恢复后 1 秒内就完成。

      路二（兜底）就算电源事件因为某些原因没送到，轮询也还在跑。进程被挂起期间
                  时钟会跳一大截，服务一旦发现"这一觉睡了 N 秒"就立刻补一次检查，
                  最坏情况 5 秒内发现。

    所以：开机查、睡眠唤醒查、休眠恢复查 —— 三种情况都覆盖。

二、计划任务 CpuPLFix（兜底，四个触发器）

    万一服务没能启动（比如被杀毒软件拦了），计划任务会在这些时机再补一刀：

      1. 开机 +1 秒，并且开机后 30 分钟内每 5 分钟重复一次
      2. 用户登录 +3 秒
      3. 系统日志出现 Power-Troubleshooter 事件 1（从低功耗状态恢复）+3 秒
      4. 系统日志出现 Kernel-Power 事件 107（系统已从睡眠状态恢复）+3 秒

    第 3、4 条就是"睡眠唤醒"和"休眠恢复"。触发后它会先预检，状态已经正常就直接
    退出、不占 CPU；不正常才修复，然后看守 4 分钟，防止固件在这段时间里再补一刀。

两个机制做的事完全一样，而且是幂等的 —— 重复执行没有任何副作用。

想确认服务在不在跑：

    2-check.bat 能看到当前状态；
    或者任务管理器 → 服务 → 找 CpuPLFixSvc。

想确认"唤醒后到底有没有检查"，看 logs\fix.log 里有没有这几行：

    [*] 收到电源事件 0x0012 (自动唤醒), 判定刚从睡眠/休眠恢复, 立即重新检查
    [*] 检测到 830 秒挂起间隔, 判定刚从睡眠/休眠恢复, 立即重新检查
    [*] 进程启动(睡眠/休眠唤醒后): 系统已运行 3600.2 秒, 解释器启动耗时 0.03 秒

> 注：如果开了"快速启动"，点"关机"再开机走的是 BootTrigger（系统仍算一次启动），
> 同样会被检查，不需要额外设置。


【要求】

    - Intel CPU（AMD 没有这套寄存器）
    - Windows 10 / 11，64 位
    - 安装时需要管理员权限

不需要安装 ThrottleStop，驱动已经内置在本目录的 TSCtl.sys 里。


【关于驱动】

读写 MSR 和物理内存必须有内核驱动。本工具已内置 TSCtl.sys，安装时复制到工具目录
并注册成服务 TSCtl（按需启动），之后由看守服务按需拉起。

这个驱动来自 ThrottleStop（作者 Kevin Glynn）。ThrottleStop 把它内嵌在自己的 exe 里，
本工具按 PE 结构把 x64 镜像连同数字签名一起提取出来，一个字节都没改，只换了个文件名
（否则会和 ThrottleStop 自己的设备名冲突）。

装好本工具后可以直接卸载 ThrottleStop，两者互不影响 —— 驱动文件在工具目录下，
服务名 TSCtl，跟 ThrottleStop 的临时驱动没有任何关联。

已知限制：如果机器开了"内核隔离 / 内存完整性"(HVCI)，Windows 可能拒绝加载这类直接
访问物理内存的驱动，安装会失败。需要先关掉内存完整性再装。


【会不会把 CPU 烧了】

不会。工具的原则是"还原系统自己的设置"，不是"超频"：

    - config.json 里 pl1_w = 0（自动，分享版默认）时，就原样把 MSR 的值写进 MMIO，
      一个瓦都不改
    - 只有 MSR 本身也被压坏（低于 15W）时，才用 CPU 标称 TDP 兜底
    - 手动填了具体瓦数时，才按填的值写

而且 CPU 自身的热保护（温度墙、EDP 电流墙）完全不受影响，该降频还是会降频。


【功耗墙填多少合适 —— 实测数据】

本机(联想 Ice Lake 工程样品, 16 线程, 标称 TDP 28W)工具首次运行前抓到的原始快照：

    MSR 0x610        = 0x004281B8002381B8    PL1 55W / PL2 55W / 35s / 66s
    MCHBAR + 0x59A0  = 0x004281B8002380A8    PL1 21W / PL2 55W / 35s / 66s

两份的 PL2 和时间常数一模一样，只有 PL1 被压到 21W。这说明 55W 是固件表里原本的
设定，21W 是固件后来在 MMIO 那份上额外加的一刀。

16 线程满载 14 秒实测（PL1 = PL2 = 55W，已锁定）：

    功耗    峰值 57.1W，稳态 47 ~ 50W
    频率    起步 3.3GHz，稳态 2.9 ~ 3.0GHz
    温度    92 -> 99 °C

结论：55W 下机器其实是被"温度墙"卡住的(99°C)，不是被功耗墙卡住。也就是说 55W
已经贴着这套模具散热能力的上限了，再往上调没有任何意义，只会更烫。

所以：

    想要满性能          pl1_w = 55   原厂 MSR 值，全核约 3.0GHz，满载 97~99°C
    折中                pl1_w = 40   全核约 2.6GHz，温度明显低一截
    原厂实际长时限值    pl1_w = 21   全核约 2.0~2.2GHz，凉且安静
    不想操心            pl1_w = 0    自动镜像 MSR，原厂怎么设就怎么用（默认）

填了具体数字就是精确目标值，调高调低都会生效。
只填 pl1_w、不填 pl2_w 时，PL2 会自动取 max(MSR 的 PL2, PL1 × 1.25)。

改完必须重启才能生效。原因见上面：bit63 一旦置 1，这个寄存器在本个开机电周期内
就变成只读，之后任何软件再写都会被硬件直接忽略。

实测验证过这一点：在 MMIO 已锁 55W 的情况下，把 MSR 0x610 改成 21W（回读确认
已写入 21.00W），满载功耗依然是 44.6W / 全核 2.91GHz，和 55W 时几乎没差别。
说明 MMIO 那份锁定后优先级高于 MSR —— 这同时也是"在 ThrottleStop 里改 55 没用"
的根本原因。锁是把双刃剑，它挡住的不仅是固件，也包括你自己。


【风扇 —— EC 档位与温度曲线】

本机的风扇转速完全由 EC 寄存器 HFSP(0x2F) 决定，Windows 里没有任何可调项
（联想 Vantage 没有散热设置；电源模式切"平衡"和"最佳性能"实测同温转速差 0.1%）。
所以工具直接写这个寄存器。

档位（本机实测，EC 温度 55~61°C 时测的）：

    HFSP    转速              说明
    0x01    2480 RPM          最安静
    0x02    2610 RPM
    0x03    2720 RPM
    0x04    3190 RPM
    0x05    3185 RPM
    0x06    3490 RPM
    0x07    3880 RPM          EC 自己曲线的天花板
    0x40    4980~5020 RPM     真满速（EC 自动永远到不了这里）
    0x80    ——                交还 EC 自动

原生自动曲线实测几乎是平的：EC 54°C 时 3861 RPM，硬扛满载到 99°C 也只有 3896 RPM
—— 它一直贴在 0x07 那一档，热到 99°C 也不肯再快。这就是"机器很烫但风扇不响"的原因。

默认曲线（config.json -> fan.curve，格式 [[温度上限, 档位], ...]）：

    ≤50°C -> 1 档    50~58°C -> 2 档    58~66°C -> 4 档
    66~74°C -> 6 档  74~82°C -> 7 档    >82°C -> 满速(0x40)

实测端到端：51°C 用 1 档(2471 RPM，比原生自动安静得多) → 67°C 升 4 档 → 77°C 升
7 档 → 85°C 以上满速；96°C 时 4983 RPM；温度掉下来自动退回 6/7 档。降温回差
1.5°C（fan.hyst），避免在档位边界来回抖。

想改：编辑 config.json -> fan.curve，不用重启（服务每分钟重读一次配置）。
想临时压住：跑 6-风扇满速.bat，它会写进配置（fan.mode = max），守护服务会一直维持，
直到你跑 5-风扇曲线.bat 恢复。手动档和自动曲线不会打架 —— 同一时刻只有看守服务在写。

注意：这个功能只对本机这种"EC 有 HFSP 寄存器"的机器有效。换别的机型如果读不到，
工具只是不动作（2-check.bat 会显示"读取失败"），不影响功耗墙那部分功能。


【EC 端口事务必须串行 —— 实测踩过的坑（重要）】

服务、命令行(bat)、临时扫描脚本读写 EC 走的都是同一套四步端口事务：
    写 CTRL=0x80(读) -> 写 DATA=偏移 -> 等 IBF 清 -> 读 DATA
实测（2026-10-18 满载扫描时）：**两个进程同时做这套事务会互相插队**，读到的其实是对方那次
事务的应答 —— 当时 0x78 读出 46，而同一刻服务读到的是 82，整段数据全不可信。应对：

    * 每个事务先拿一把跨进程命名互斥体 Global\CpuPLFix-EC（服务与命令行共用同一把，
      Global\ 才能跨会话：服务在 session 0，bat 在用户会话）；拿不到就退化成不加锁，
      不影响功能。
    * 关键读数（温度 0x78、标志 0x89/0x8A/0x8B）都做**一致性校验**：连读两次一致才认，
      不一致就加大等待重试，仍不一致就当"这次没读到"（沿用上一轮的判断）——
      绝不拿垃圾值去改保护等级。
    * 每次读之前还先等一会儿（3ms，重试时 8/20ms）：EC 满载时自己忙不过来，不等就会读到
      上一次留在输出缓冲里的**残留字节**（实测"读 0x8A"读到的是 0x7A 的值 46，还连读两次一样）。
    * 温度突变也过滤：3 秒内跳 15°C 以上当可疑值，本轮沿用上一次，下一轮还是这样就认。
    * 固件标志必须**连续两轮都读到**才动手，单轮毛刺只记一行提示。

另外：**不要用 WMI 的 MSAcpi_ThermalZoneTemperature 去读热区温度** —— 本机那个查询会把
调用方永久挂死（实测把一个后台进程卡了 20 分钟，只能强杀）。本工具用的是 EC 寄存器和 DSDT
反汇编，不碰它。


【过热保护 —— 别让固件把你强制休眠】

本机固件设了 ACPI 热区 \_TZ.THM0 的 _HOT = 401K（≈127.9°C）：热区摸到它就
直接强制休眠（S4）。2026-10-18 12:43 跑满载实测触发过一次，系统日志里的原话是
"由于严重的热事件，系统已进入休眠状态…高级配置和电源接口热区域 = \_TZ.THM0
_HOT = 401K"（Kernel-Power 事件 88 + 42）。

后来把本机 DSDT 里 \_TZ.THM0 的反汇编翻出来（_TMP / _CRT / _HOT / TC2K），才搞清
固件到底按什么判 —— 结论跟"两边差多少度"这种线性想法完全不是一回事：

  * _TMP（热区报给系统的温度）平时返回的就是 EC 寄存器 0x78 换算出来的值：
        温度 = 0x78 * 10 + 2732     （单位 0.1K，所以 0x78 本身就是摄氏度）
  * _HOT = TCRT - 1 = 4010（= 401.0K ≈ 127.9°C）
  * 但"温度路线"根本走不到 4010：0x78 = 127 只能算出 400.2K，而 0x78 = 128（0x80）
    是固件约定的"无效码"，AML 会把它当成 48°C。**光靠温度值，热区永远到不了 _HOT。**
  * 真正让 _TMP 直接返回 _HOT 的是 EC 自己的过热标志寄存器：
        Local1 = RBEC(0x89) & 0x7F
        Local2 = RBEC(0x8A) & 0x7F
        Local3 = RBEC(0x8B) & 0x7F
        If (Local3) { ... Return (TCRT - 1) }      ← 直接报 _HOT
        If (Local1) { ... Return (TCRT - 1) }

  这三个寄存器（低 7 位）任何一个非零，热区立刻被报成 127.9°C，系统和固件就执行
  强制休眠。**12:43 那次就是它们触发的，跟当时 0x78 读 99 还是 120 无关。**

所以本工具分两条线看：

  1) 温度线（预防，主力）：EC 0x78 到阈值就砍功耗墙 + 风扇拉满。
     0x78 是实测唯一能"提前知道要热了"的读数（它跟热区同一来源，只是量程上限只到
     ~99，越接近上限越迟钝）。
  2) 固件标志线（最高级）：0x89/0x8A/0x8B 一置位 —— 说明固件已经在报 _HOT，
     这是它动手前的最后信号。立刻压到最低功耗墙 + 风扇满速；若
     guard.escape_hibernate = true，就直接主动优雅休眠（先落盘，比被强制断电好）。

默认阈值（config.json -> guard）：

    预警  EC ≥ 93°C   -> 功耗墙压到 PL1=20W/PL2=25W，风扇满速
    严重  EC ≥ 96°C   -> 功耗墙压到 PL1=10W/PL2=12W，风扇满速
          （CPU DTS ≥ 97°C 也算严重）
    固件标志  0x89/0x8A/0x8B 任一低 7 位非零 -> 同"严重"，并按需主动休眠
    逃生  EC ≥ 105°C  -> 维持最低功耗墙；guard.escape_hibernate = true 时主动休眠
    解除  EC ≤ 78°C   -> 自动恢复原来的 AC / 电池档

保护只影响本工具进程，不改 config.json；解除后功耗墙自动恢复，不需要重启。
日志里每一级变化留一行，2-check.bat 会显示"最近一次保护记录"和三个标志寄存器当前值。

阈值为什么这么定（诚实版）：

  * 我们看不到 EC 内部那颗真正决定"什么时候置标志"的传感器，所以温度线只能是
    "提前降温"，不是精确卡阈值。
  * 0x78 实测到 ~99 就上不去了：93/96 这两档离它的量程上限只剩几度，属于贴着上限
    动手 —— 晚（不打扰日常）但余量薄。所以你会看到 EC 温度长时间停在 93~96，
    那是被我们自己砍功耗压在那儿的，正常。
  * 真正把温度打下来的是功耗墙（发热由功耗决定），风扇只是辅助：本机原生自动曲线
    几乎是平的（54°C→3861 RPM，99°C→3896 RPM），写满速档才有 ~5000 RPM。
  * recover_c = 78 是有意的：压到 70 的话，触发一次后大热天满载可能长期卡在 20W
    上不来，你会觉得"机器莫名变慢"。

想更保守 / 更激进：改 config.json -> guard 里的 warn_c / crit_c / escape_c /
recover_c 和对应瓦数即可；不想让固件标志参与判级，把 guard.trip_flags 改成 false。


【日志】

    logs\fix.log    每次运行的完整记录。

每次都会记下修复前后的原始寄存器值，十六进制，例如：

    修复前: MSR 0x610=0x004281B8002381B8 PL1=55.00W PL2=55.00W | MMIO +0x59A0=0x004281B8002380A8 PL1=21.00W PL2=55.00W lock=0
    目标    : PL1=55.00W PL2=55.00W (35秒/66秒), 锁定
    修复后: MMIO 0x804281B8002381B8 PL1=55.00W PL2=55.00W lock=1  [√] 已生效并锁定

开机那条还会记录"系统已运行多少秒""解释器启动耗时"，用来判断到底是任务启动晚了，
还是执行本身慢了。日志里会标明这次是哪种触发：

    [*] 进程启动(开机): 系统已运行 24.0 秒 ...              ← 冷启动
    [*] 进程启动(睡眠/休眠唤醒后): 系统已运行 3600.2 秒 ...   ← 唤醒后由计划任务触发
    [*] 收到电源事件 0x0012 (自动唤醒) ...                   ← 唤醒后由服务捕获

服务就绪时还会记一行，用来确认电源事件订阅成功：

    [*] 已订阅电源事件(SERVICE_ACCEPT_POWEREVENT): 睡眠/休眠恢复后 1 秒内响应; 另有 2 秒轮询兜底

想看"降频那一刻固件到底把功耗墙压到了几瓦"，就看开机后第一条记录的 MMIO PL1
—— 那是固件刚写完、工具还没动手时的现场值。反馈问题时把这个文件带上。


【卸载】

    9-uninstall.bat

会删除：看守服务 CpuPLFixSvc、计划任务 CpuPLFix、驱动服务 TSCtl。
（如果机器上还留着早期独立风扇脚本的计划任务 ThinkFanCurve，也一并清掉。装好本工具后
  风扇已经由看守服务统一管，不再需要那个任务。）
不动文件，也不影响 ThrottleStop 本身。


【已知限制】

    - 只处理 PL1/PL2 这一条路径。如果是 BD PROCHOT、温度墙、电池/适配器识别问题
      导致的降频，本工具管不了，那种情况还是得用 ThrottleStop 排查。
    - 不同机器 MMIO 的功耗墙寄存器偏移可能不同。本工具按 0x59A0 处理（Intel 近几代通用）。
      如果你的机器不是这个偏移，2-check.bat 会显示读不到或数值明显不对。
    - CPU 被锁在 0.40GHz 时，Windows 自身启动就慢十倍，任何用户态程序都只能等系统
      把服务拉起来。所以从按下电源到修复完成，正常在 10~40 秒之间，无法做到"零延迟"。
      本机实测：服务在开机 23.5 秒完成修复，计划任务 24.0 秒起来时发现已经是好的。
      睡眠/休眠唤醒不受这个限制 —— 服务本来就活着，唤醒后 1~5 秒就补锁完成。
    - 过热保护是"提前降温"，不是"精确卡阈值"：EC 内部那颗真正决定何时置 _HOT 标志的
      传感器读不到，工具只能靠 EC 温度(0x78)提前动手 + 固件标志(0x89/0x8A/0x8B)兜底。
      极端情况（比如散热口被捂住、环境 40°C 又跑满 AVX 负载）仍有可能摸到 401K。
      要更保险就把 guard.warn_c 往下调（比如 80）。
    - 风扇控制只写 EC 寄存器，绕过了 EC 自己的调速逻辑。如果哪一步写错档位，跑一次
      7-风扇交还EC自动.bat（0x80）就能完全恢复原样 —— 不会损坏硬件。
    - 过热保护里的"主动休眠"默认关闭（guard.escape_hibernate = false）。想让它真到
      105°C 就替你休眠，把那个值改成 true。
